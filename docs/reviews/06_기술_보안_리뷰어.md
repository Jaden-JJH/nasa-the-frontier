# 역할 6, 기술과 보안 리뷰

로버 복구가 운전자 동의 없이 만충 로버를 기지로 순간이동시켜, 물 원정과 협력의 핵심 루프를 정상 조작만으로 무너뜨린다. 프롬프트의 홀드 시간도 서버가 검증하지 않아 행동 시간이 클라이언트 설정에 달려 있고, 캐릭터 초기화는 산소 구조 비용을 우회한다. 에뮬레이터가 실제 엔진과 다른 경계 상자를 반환해 기본 패널 배치 결함을 가리는 반례도 확보했다. 테스트 통과를 공개 데모 준비 완료로 판단하면 안 된다. 현재 확정한 심각도는 높음 4건, 중간 7건, 낮음 1건이며, Studio 실행 없이 치명 등급을 단정하지 않았다.

## 발견 사항

### 1. 복구 콘솔로 정상 운전자를 버리고 만충 로버만 회수한다

- 심각도: 높음.
- 근거: `src/server/RoverRecovery.luau:45`, `:54`, `:73`, `:146`. 수동 복구는 phase만 검사하고, 운전자 존재, 고장 여부, 재사용 간격을 검사하지 않는다. 탑승자를 먼저 내린 뒤 로버만 홈으로 옮기고 기존 탱크량을 보존한다. 임시 실행에서 채취 직후 tank 40, 복구 후 tank 40, 홈과 거리 0을 확인했다.
- 반례 시나리오: 학생 A가 얼음에서 물을 채우자 기지의 학생 B가 콘솔을 누른다. A는 얼음에 남고 B는 돌아온 로버에서 40W를 하역한다. B가 반복하면 협력 상대를 야외에 가두는 기능이 되고, 합의해서 쓰면 귀환 운송 비용이 사라진다.
- Studio 재현 절차: 2인 서버를 시작한다. A가 로버로 얼음에 가서 3초 홀드로 40W를 채우고 계속 앉아 있는다. B가 착륙선 콘솔에서 E를 1초 누른다. B가 회수된 로버 옆 물탱크에서 하역한다.
- 예상 증상: 운전자 하차, 로버만 기지로 이동, 탱크 40 유지, 물 +40, 운전자 야외 잔류. 물리적으로 하차한 캐릭터의 최종 위치는 Studio에서 확인해야 하지만 코드에는 캐릭터 귀환 처리가 없다.
- 목적 피해: 물류와 위험을 계산하는 과제를 복구 버튼으로 대체하고, 다른 학생의 생존을 본인 의사와 무관하게 훼손한다.
- 구체적 제안: 수동 복구는 `Occupant == nil`일 때만 허용한다. 수동 복구 시 탱크를 0으로 만들고 상태와 Attribute를 함께 송신한다. 기지 전체에 10초 재사용 제한을 둔다. 자동 복구의 만충 보존 정책도 동일하게 정해 수동 경로를 우회하지 못하게 한다.
- 예상 작업량: M, 반나절. 운전자 잔류와 탱크 소실 안내까지 2인 검증이 필요하다.

### 2. 행동 홀드 시간을 서버가 믿고, 일부 프롬프트에는 자체 거리 검사도 없다

- 심각도: 높음.
- 근거: `src/server/SolarPanels.luau:90`, `src/server/Construction.luau:87`, `src/server/WaterLoop.luau:56`, `:87`, `src/server/RoverRecovery.luau:146`. 패널 2초, 얼음 3초, 건설 0.5초의 경과 시간을 검사하는 서버 기록이 없다. 패널, 건설, 하역 요청자는 캐릭터와 상호작용 대상의 거리도 자체 검사하지 않는다. 임시 실행에서 시간 증가 0초에 패널 3장이 설치되었다.
- 반례 시나리오: 학생의 변조 클라이언트가 가까운 설치대에서 로컬 `HoldDuration`을 0으로 바꾸고 E를 세 번 누른다. 나머지 학생이 6초를 쓰는 작업을 즉시 끝내고 원정에 출발한다. 하루 3장 제한은 유지되지만 시간 배분 과제가 달라진다.
- Studio 재현 절차: Play의 클라이언트 Command Bar에서 설치대 프롬프트의 `HoldDuration`만 0으로 바꾼다. 설치대 가까이에서 E를 세 번 누른다. 얼음에서도 운전석에 앉은 채 같은 방법으로 3초 채취를 생략한다.
- 예상 증상: 서버가 원래의 2초 또는 3초를 기다리지 않고 설치와 만충을 수락한다. 서버의 HoldDuration 속성이 원래 값인 것만 확인하는 스모크는 이 공격을 검출하지 않는다.
- 목적 피해: 행동 시간을 전제로 한 역할 분담과 자원 의사결정이 클라이언트 수정으로 무력화된다.
- 구체적 제안: 서버에 플레이어별 홀드 시작 시각을 저장하고 완료 시 거리, 생존, phase, 최소 경과 시간을 다시 검사한다. 시작 이벤트 자체도 신뢰하지 말고 거리 검증을 적용한다. 완료 후 기록을 소비한다. 거리 기준은 기존 `distanceToPart`를 써 12 studs와 지연 여유 2 studs로 통일하고, 얼음은 현재의 운전자와 로버 거리 조건을 추가로 유지한다.
- 거리 공격의 판정 한계: 사용자 공격 가정대로 먼 거리의 Triggered가 처리기에 도달하면 자체 검사 없는 경로는 수락한다. 다만 현행 공식 문서는 Triggered 자체에는 엔진의 서버 거리 검사가 있다고 명시한다. 따라서 처리기 검증 누락과 실제 엔진을 뚫은 원격 발동 성공은 구분한다. 홀드 변조와 Enabled 우회 가능성은 공식 문서에도 명시되어 있다. [Roblox 클라이언트와 서버 경계 보안](https://create.roblox.com/docs/scripting/security/client-server-boundary#proximityprompt)
- 예상 작업량: M, 반나절.

### 3. 캐릭터 초기화가 산소 구조 비용을 무료로 우회한다

- 심각도: 높음.
- 근거: `src/server/Oxygen.luau:103`, `:164`, `src/server/LandingSite.luau:236`. 산소 고갈에서만 Food -1, Water -2를 적용한다. 다른 사유로 캐릭터가 생성되면 산소 100을 지급하고 착륙선으로 옮긴다. 일반 사망과 초기화에 비용을 부과하는 경로가 없다. 임시 실행에서도 CharacterAdded 후 산소 100, 고갈 횟수 증가 0이었다.
- 반례 시나리오: 교사가 야외 산소 관리와 구조 비용을 설명한 뒤 학생이 산소 1에서 Roblox 캐릭터 초기화를 누른다. 기지로 무료 귀환하고 산소가 가득 찬다. 만충 후 초기화하고 1번 복구를 쓰면 혼자서도 물 귀환 운송을 생략한다.
- Studio 재현 절차: Play에서 실외에 50초 이상 머문다. 산소가 0이 되기 전에 Roblox 메뉴의 캐릭터 초기화를 실행한다. 재생성 전후 Food, Water, oxygenDeaths와 산소를 비교한다.
- 예상 증상: 일일 소비 이외의 구조 비용이 없고 고갈 횟수도 증가하지 않지만, 산소는 100으로 회복되고 기지에 도착한다.
- 목적 피해: 생존 실패와 자원 페널티의 인과관계가 입력 방식에 따라 달라진다.
- 구체적 제안: playing 중 발생한 모든 캐릭터 사망과 초기화에 동일한 구조 비용을 적용한다. 첫 스폰, selecting 중 재생성, 이미 산소 구조를 처리한 캐릭터는 제외하도록 캐릭터별 처리 완료 플래그를 둔다. CharacterAdded에서는 충전과 위치 복구만 맡긴다. 메뉴 버튼만 막는 조치는 변조 클라이언트의 사망 유발을 막지 못한다.
- 예상 작업량: M, 반나절.

### 4. Clone이 nil을 반환하는 정상 엔진 조건에서 기지 조립 전체가 중단된다

- 심각도: 높음.
- 근거: `src/server/KitImports.luau:325`, `:360`, `:363`, `:367`, `:373`, `src/server/DevMap.luau:1338`, `:1679`, `src/server/Main.server.luau:11`. 원본의 파트 존재만 검사하고 `Archivable`과 복제 결과를 검사하지 않는다. 실제 Roblox는 Archivable false인 루트의 Clone에 nil을 반환한다. 검토 환경의 Lune은 같은 입력으로 `KitImports.take`를 오류 없이 통과시켰다. 이것은 명세와 에뮬레이터의 직접적인 차이다. [Roblox 공식 Instance 명세](https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/Instance.yaml)
- 반례 시나리오: 에셋 담당자가 런타임에 복제 금지로 설정한 Lander를 전달한다. 개발자는 이름과 파트 존재 검사가 통과한 것을 보고 시연을 시작하지만 부팅이 멈춘다. Model이면 GetDescendants에서, 단일 Part이면 `part.Parent`에서 nil 접근이 발생한다.
- Studio 재현 절차: 별도 테스트 플레이스에서 Main을 비활성화하고 Workspace.KitImports에 Lander라는 Part를 넣는다. Play 후 서버 Command Bar에서 해당 Part의 Archivable을 false로 바꾼다. 이어 Main을 활성화한다. 이렇게 해야 편집 파일 저장 과정의 Archivable 제외와 런타임 Clone 동작을 혼동하지 않는다.
- 예상 증상: `cloneAsModel`의 nil 접근 오류, `DevMap.ensure` 중단, `GameFlow.start` 미실행. Remotes는 생성되었어도 초기 상태와 선택 화면은 진행하지 않는다.
- 목적 피해: 학생과 심사위원 모두 첫 화면 이후 진행할 수 없고, 그레이박스 대체 약속도 작동하지 않는다.
- 구체적 제안: Clone 직후 결과를 검사하고 복제본에 실제 파트가 남았는지도 다시 확인한다. 실패하면 경고 한 번과 nil을 반환해 해당 역할만 그레이박스로 대체한다. Archivable false인 자식들만 들어 있는 원본도 같은 검사에 포함한다. 개념 코드는 다음 4줄이다.

```luau
local cloned = source:Clone()
if not cloned or not hasParts(cloned) then
    return nil, false
end
```

- 예상 작업량: S, 1시간 안. 반환 타입과 두 분기의 복제 처리를 함께 바꿔야 한다.

### 5. 기본 패널도 실제 GetBoundingBox에서는 방향이 되돌아가 슬롯을 넘친다

- 심각도: 중간.
- 근거: `src/server/DevMap.luau:1695`, `:1707`, `src/server/SolarPanels.luau:43`, `tests/server_smoke.luau:275`, `:297`. 긴 축이 Z인 Panel을 Y축 90도로 돌린 뒤 그 파트를 PrimaryPart로 잡는다. Roblox의 경계 상자는 PrimaryPart 또는 피벗 방향을 따르지만, 모사는 회전을 무시한 월드 축 상자와 위치 CFrame만 반환한다. `placeOnTop`은 경계 상자 방향을 슬롯 방향으로 맞추므로 실제 엔진에서는 앞서 적용한 패널 회전까지 취소한다. [Roblox 공식 Model 명세](https://github.com/Roblox/creator-docs/blob/main/content/en-us/reference/engine/classes/Model.yaml)
- 반례 시나리오: 디자이너가 스모크와 같은 1.29 x 1.10 x 1.67 크기의 Panel을 넣는다. 테스트상 점유율은 X 95%, Z 91.73%다. 공식 명세의 경계 상자 계산으로 같은 소스를 실행하면 X 73.38%, Z 118.75%가 된다. 학생은 설치한 패널이 슬롯 밖으로 길게 튀어나온 것을 본다.
- 검증 방법과 한계: 임시 모사에서 GetBoundingBox의 방향만 PrimaryPart 기준으로 바꾸어 위 수치를 재현했다. Studio 화면 확인은 하지 않았다. 재현은 새 플레이스의 KitImports.Panel에 위 크기의 단일 Part를 넣고 패널 1장을 설치하면 된다.
- 목적 피해: 자동 스케일과 슬롯 배치의 신뢰가 깨지고, 패널 크기 조정에 쓴 작업을 다시 반복하게 된다.
- 구체적 제안: 조립 때 결정한 외형 방향을 보존하고, 슬롯 좌표계의 8개 모서리로 바닥과 중심을 계산해 평행 이동한다. 피벗 방향이 다른 상태에서 GetBoundingBox의 Y를 월드 높이로 사용하지 않는다. 기본 Panel, Yaw 90, 기울어진 피벗, 여러 파트 모델을 각각 검사한다.
- 예상 작업량: M, 반나절.

### 6. 잘못된 맵을 경고만 하고 진행시켜 완공 불능과 보이지 않는 발전을 만든다

- 심각도: 중간.

현재 클라이언트의 FireServer는 SelectSite, SetSpeed, RequestRestart 세 종류뿐이다. 서버 송신용 StateUpdate, OxygenUpdate, Notify, SiteSelectionOpen, LandingSequence, GameOver에는 OnServerEvent 처리기가 없어 이를 FireServer한다고 자원을 바꾸는 경로는 없다. 프롬프트 인자 혼동도 발견하지 않았다. 개별 ProximityPrompt.Triggered는 Player 하나, ProximityPromptService.PromptTriggered는 Prompt와 Player이며 현재 코드가 사용하는 형태는 맞다.

### 상태 일관성과 실행 순서

| 질문 | 추적 결과 |

| 단일 테이블의 publish 없는 정상 변경 | ResourceState:20은 실제 테이블을 노출하지만 현재 src에서 이를 직접 수정하는 호출자는 찾지 못했다. set과 patch는 자체 송신하지 않으나 정상 게임 변경 경로는 뒤에서 publish한다. 테스트의 송신 없는 patch는 준비 작업이다 |

| 2배속 전환 | GameClock:85의 `남은 시간 x 이전 배속 / 새 배속` 계산은 남은 게임 시간을 보존한다. generation 증가와 기존 대기 스레드 취소도 있다. 배속 토글로 하루를 무한 연장한다는 결함은 발견하지 못했다. 현재 스모크는 중간 시점의 정확한 다음 틱 시각까지 검사하지 않는다 |

## 실행 우선순위 요약

### 데모 전 반드시

- 1번, 만충 회수와 타인 강제 하차를 차단한다. 2인 서버에서 운전자 탑승 중 복구가 거부되고 수동 복구 뒤 물이 보존되지 않는 것을 확인한다.
- 2번, 홀드 시간과 상호작용 거리를 서버에서 검증한다. 로컬 HoldDuration 0으로 패널과 얼음 작업을 즉시 완료할 수 없어야 한다.
- 3번, 캐릭터 초기화와 사망에도 동일한 구조 비용을 적용한다. 산소 1에서 초기화한 결과와 실제 산소 고갈 결과가 일치해야 한다.
- 4번, 복제 불가 에셋을 역할별 그레이박스로 대체한다. 잘못된 Lander 하나로 GameFlow 부팅이 중단되지 않아야 한다.
- 5번과 6번, 실제 엔진의 패널 배치를 확인하고 필수 맵 구조를 시작 전에 검증한다. 최종 제출 플레이스에서 A, B, C 완공을 한 번 끝낸다.
- 7번과 9번, 레이더는 점 3개를 유지하고 -0.2E/일은 음수로 보여 준다.
- 10번, 추가 Lune 반례와 2인 Studio 완주 결과를 구분해 기록한다. 259개 통과만으로 엔진과 화면 검증을 대체하지 않는다.

### 있으면 좋음

- 8번, 배속 공통 간격과 토스트 경고 보존을 넣는다. 누군가 속도를 반복 변경해도 산소 경고를 3초 읽을 수 있어야 한다.
- 11번, 현재 코드의 실제 크기와 기존 BaseKit 보존 정책으로 문서를 맞춘다.
- 12번, 늦은 Attribute와 중복 ModuleId를 처리하고 반복 시연 후 PadSign 수를 확인한다.
- 10번의 수신 경계 검증을 적용해 잘못된 상태 한 번이 해당 프레임의 전체 화면 전환을 중단하지 않게 한다.

### 하지 말 것(과잉 설계 경고)

- 해커톤 전에 범용 차량 안티치트, 투표 기반 권한 시스템, 전체 물리 에뮬레이터를 새로 만들지 않는다. 현재 세 Remote와 여섯 종류 프롬프트의 조건부터 닫는다.
- 상주 루프에 generation이 없다는 이유만으로 모두 재작성하지 않는다. 판마다 시작되는 시계와 서버당 한 번 시작되는 감시 루프를 구분한다.
- 프레임 측정 없이 바위 170개를 모두 제거하거나 Neon 행성을 원인으로 단정하지 않는다. 현재 확정된 10Hz 중복 탐색부터 없앤다.
- 클라이언트 nil을 임의의 0으로 바꿔 게임 자원처럼 표시하지 않는다. 서버 상태의 누락과 실제 자원 고갈을 혼동시키기 때문이다.

## 확신 낮음 항목

- 실제 Roblox 네트워크에서 먼 거리 Triggered가 도달하는 조건은 검증하지 못했다. 애플리케이션 자체 검증 누락은 코드로 확인했고, 현재 공식 문서는 Triggered의 엔진 거리 검사를 명시한다. 원격 발동 성공을 확인했다고 보고하지 않는다.
- Terrain 윗면 -0.5와 콘크리트 판 0.5 사이의 1 stud 차이가 복셀화 이후에도 충분한지, 경사로와 실제 바퀴가 걸리는지는 화면과 물리 확인이 필요하다. 호출 좌표만으로 패드 재매몰을 확정하지 않는다.
- 복구 직후 플레이어 위치, SeatWeld 제거 지연, Humanoid 상태 전이, 로버 네트워크 소유권과 조향 안정성은 2인 Studio 검사 대상이다. 개발자의 W 전진 확인 기록을 부정하지 않는다.
- 늦은 CharacterAdded, RootPart와 Head 생성 지연, Pad Attribute 복제 순서, StreamingEnabled의 실제 설정은 저장소만으로 확정할 수 없다. 12번의 참조 유실 조건과 별개로 기본 제출 플레이스에서의 발생 빈도는 미확인이다.
- 패널 73.38% x 118.75%는 공식 명세에 맞춘 기하 실험값이다. 실제 메시 피벗과 최종 화면에 대한 Studio 확인은 남아 있다.
- 태양 텍스처의 실제 표시, DoubleSided 변경 성공, 건물 안쪽 면, 행성의 GPU 비용과 교실 기기의 FPS는 Lune으로 입증하지 못했다.
