# 역할 4. 로블록스 플랫폼 활용 리뷰

검토 기간: 2026-10-17부터 2026-10-18 KST. 대상은 현재 작업 트리이며, 커밋되지 않은 변경도 포함한다. GDD를 먼저 읽고 서버 모듈 15개 전체, 클라이언트 진입점, Remotes, 프로젝트 설정, CONTRACT, SETUP 5절, MAP_SPEC을 대조했다. 판정에 필요한 클라이언트 UI와 에셋 가이드도 추가로 읽었다. 작업량은 S 1시간 안, M 반나절, L 하루 이상이다. 아래 수치 중 성능 목표와 수정 후 동작은 제안이며 측정 결과가 아니다.

## 1. 총평

가장 치명적인 문제는 Public 설정과 게임 링크만으로 중학생에게 배포할 수 있다고 전제한 제출 절차다. 현재 공식 공개 조건에는 계정 연령 확인과 대상 연령별 추가 요건이 있으며, 실제 배포 계정의 자격은 확인되지 않았다. 접속에 성공해도 같은 링크가 같은 기지를 보장하지 않고, 준비되지 않은 동료를 기다리는 절차도 없다. 게임 안에서는 운송 중인 로버를 물과 함께 순간 귀환시키는 복구, 누구나 바꾸는 배속과 즉시 재시작이 협력과 자원 판단을 훼손한다. 멀티플레이 복제는 사용하지만 협력의 책임, 의사 전달, 공동 결정은 거의 구현하지 않았다. 이 상태에서는 로블록스 선택의 핵심인 학생 접근성과 협력을 입증하기 어렵다.

## 2. 발견 사항

### F01. Public만 켜면 학생에게 배포된다는 제출 절차가 성립하지 않는다

- 심각도: 치명
- 근거: `docs/SETUP.md:125`의 제출 절차는 Publish, 최대 4명, Public, 다른 계정 접속 확인뿐이다. 실제 Creator Dashboard 설정과 제출 URL은 저장소에 없다. 현재 공식 문서는 16세 이상 공개에도 제작자 연령 확인 등을 요구하고, 16세 미만 도달에는 추가 자격, 평가, 전체 Maturity & Compliance 설문을 요구한다. 학생 대상 공개가 Public 토글만으로 끝난다는 전제가 틀렸다. [공식 공개 조건](https://create.roblox.com/docs/production/publishing/publish-games-and-places), [공식 대상 연령별 안내](https://en.help.roblox.com/hc/en-us/articles/203313890-How-to-Publish-Games-on-Roblox)
- 반례 시나리오: 교사가 14세 학생 네 명에게 링크를 보낸다. 제작자 계정에서는 실행되지만 학생 계정에는 이용 불가 화면이 나온다. 학생은 달 기지를 보기 전에 체험에서 제외되고, 심사위원에게 학생 사용자층을 선택한 근거도 설명하지 못한다.
- 목적에 해로운 이유: 교육 대상 자체가 들어오지 못한다. 계정 생성, 로그인, 앱 설치가 끝나지 않은 심사위원도 15분을 게임 밖에서 소비한다. 게스트 접속을 제출 경로로 삼을 수 없다.
- 구체적 제안: 제출 전 제작자 한 명을 배포 책임자로 정하고 Creator Dashboard의 공개 자격, 대상 연령 도달 상태, 설문 결과, Public, MaxPlayers 4를 실제 화면으로 기록한다. 제작자 권한이 없는 성인 계정과 실제 대상 연령의 허가된 테스트 계정으로 각각 Roblox Player에서 입장한다. 심사위원에게 계정과 앱이 필요하다는 안내를 제출 설명 첫 문장에 넣는다. 계정 자격과 학생 공개가 해결되지 않으면 학생 체험 가능이라고 제출하지 말고, 접근 가능한 시연 계정의 현장 플레이와 2분 녹화본을 별도 대안으로 준비한다. 개인정보나 타인의 비밀번호를 수집하지 않는다.
- 예상 작업량: 확인과 제출 안내 S. 연령별 공개 자격과 외부 평가 대기는 팀 작업만으로 완료 시간을 보장할 수 없다.

### F02. 로버 복구가 물 운송을 순간 이동으로 바꾸고 운전자를 버린다

- 심각도: 높음
- 근거: `src/server/RoverRecovery.luau:45`는 탑승자가 있어도 하차시킨 뒤 로버를 홈으로 이동한다. `:73`은 기존 탱크를 다시 반영한다. `:146`의 수동 요청은 playing만 검사하며 요청자, 탑승자 동의, 복구 간격을 검사하지 않는다. `src/shared/Simulation.luau:394`는 귀환한 탱크를 그대로 기지 물에 더한다.
- 반례 시나리오: 학생 A가 얼음에서 40W를 채우자 기지의 B가 1초 홀드로 복구한다. 로버와 물은 즉시 기지에 도착하고 A는 얼음 옆에 내려진다. B는 물을 하역하고, A는 산소가 줄어드는 화면을 본다. 협조하면 귀환 주행을 생략하고, 장난치면 원정자를 반복해서 버릴 수 있다. 익스플로잇도 필요 없다.
- 목적에 해로운 이유: 얼음 거리와 운송 시간의 비용을 학습하는 핵심 루프가 무너진다. 정상 기능을 누른 동료 때문에 구조 페널티까지 생겨 협력이 불신으로 바뀐다.
- 구체적 제안: 수동 원격 귀환은 무인 상태 10초 이상, 홈에서 30 studs 이상 떨어졌을 때만 허용하고 로버 전체에 15초 쿨다운을 둔다. 홈으로 옮기는 복구는 탱크를 0으로 만든다. 탑승 중에는 수동 귀환을 거부한다. 추락으로 탑승자를 강제 구조하는 자동 복구에서는 탑승자도 착륙선으로 보내고 물을 잃었다고 알린다. 전복만 해결하는 경우는 현장에서 자세를 바로잡아 귀환 순간 이동과 구분한다.
- 예상 작업량: M

### F03. 시작 버튼을 누르지 않은 플레이어도 자동 선택과 생존 시간에 끌려간다

- 심각도: 높음
- 근거: `src/client/Main.client.luau:78`의 시작 버튼은 로컬 `titleDismissed`만 바꾼다. `src/server/LandingSite.luau:97`은 첫 플레이어에게 권한을 주는 즉시 30초 선택 타이머를 시작하고, `:195`는 5초 후 게임을 진행한다. `src/server/GameFlow.luau:172`는 입장 때 상태를 보내지만 UI 준비 확인과 재요청 경로는 없다. `src/shared/Remotes.luau:14`에도 준비 완료 이벤트가 없다.
- 반례 시나리오: 교사가 먼저 들어와 설명하는 동안 학생은 타이틀을 읽고 있다. 30초 뒤 패드 2가 자동 선택되고 5초 뒤 자원이 줄어든다. 늦게 시작 버튼을 누른 학생은 선택 이유도 배우지 못한 채 진행 중 기지에 투입된다. playing 중 늦게 들어온 학생에게는 현재 팀 미션만 보이며 개인 조작 입문은 없다.
- 목적에 해로운 이유: 착륙지 선택의 학습 기회를 접속 순서가 결정한다. 첫 설치와 첫 물 원정을 경험하지 않은 학생에게 Lab 착공 미션이 내려오면 협력보다 따라잡기가 과제가 된다.
- 구체적 제안: UI 이벤트 연결을 마친 클라이언트가 `ClientReady`를 한 번 보내면 서버가 현재 상태, 선택 정보, 회차 ID를 회신한다. 별도의 시작 버튼으로 준비 상태를 올린다. 준비된 권한자의 시작 동작 후에만 선택 타이머를 시작하고, 최소 1명 준비와 교사 시작을 조건으로 둔다. 늦은 입장자는 게임을 멈추지 않고 3단계 조작 안내를 받게 한다. 준비 요청은 플레이어별 초당 1회로 제한한다. RemoteEvent의 버퍼가 있으므로 현재 초기 이벤트가 항상 유실된다고 단정하지 않는다. 문제는 준비 여부와 진행 여부를 연결하는 계약이 없다는 점이다.
- 예상 작업량: M

### F04. 한 명의 배속 변경과 재시작이 다른 세 명의 판단을 무효화한다

- 심각도: 높음
- 근거: `src/server/GameFlow.luau:139`의 SetSpeed는 1 또는 2, playing, 플레이어별 1초 간격을 검사하지만 권한은 검사하지 않는다. `:164`의 재시작은 won 또는 lost면 누구든 즉시 실행한다. `src/shared/Config.luau:29`, `:91`에서 하루는 10초이고 로버 최대 속도는 18 studs/s다. 배속은 이동과 채취 홀드 시간을 단축하지 않는다.
- 반례 시나리오: A와 B가 가동 중이고 전력이 충분하며 물이 20인 Pad1 기지에서 하루 틱 직후 원정자가 출발한다. 하루 물 소비는 크루 1, A 1, B 2로 합계 4다. 중심 거리 450 studs를 왕복하는 주행 계획을 단순 계산하면 900 / 18 + 3으로 약 53초다. 이는 실제 정차 거리와 출발 위치를 반영한 실측 시간이 아니다. 동료가 2배속을 켜면 물 부족 3일 연속까지 7틱, 35초여서 귀환 전에 실패할 수 있다. 1배속의 같은 여유는 70초다. 실패 결과를 교사가 읽는 순간 다른 학생이 재도전을 눌러 화면도 지운다.
- 목적에 해로운 이유: 물 여유와 이동 시간을 비교해 내린 판단이 동료의 숨은 조작으로 바뀐다. 결과를 보고 선택을 되짚는 수업 단계도 보장하지 못한다.
- 구체적 제안: 교사 또는 현재 진행 책임자 한 명만 SetSpeed와 RequestRestart를 실행하게 한다. 책임자 퇴장 시 남은 준비 완료 플레이어에게 이양한다. 배속 변경 간격은 서버 전체 5초로 두고 변경자와 새 배속을 전원에게 표시한다. 결과 화면은 최소 10초 유지한 뒤 책임자에게 재시작을 연다. 2배속 버튼에는 물 소비 속도가 빨라지고 운전 속도는 같다는 문구를 붙인다.
- 예상 작업량: S

### F05. 프롬프트 홀드 시간과 요청 빈도를 서버가 검증하지 않는다

- 심각도: 높음
- 근거: `src/server/SolarPanels.luau:90`, `src/server/Construction.luau:87`, `src/server/WaterLoop.luau:56`, `:87`은 Triggered에서 곧바로 규칙 함수를 실행한다. 서버가 2초 설치, 3초 채취의 경과 시간을 재지 않는다. 거부 요청도 알림과 상태 복사 작업을 발생시킨다. `src/server/RoverDrive.luau:22`는 생존과 거리를 검사하지만 phase 게이트가 없다. 공식 문서상 Triggered에는 엔진의 거리 검사가 있지만 HoldDuration과 Enabled만으로 보안을 보장할 수 없다. [클라이언트 경계 보안](https://create.roblox.com/docs/scripting/security/client-server-boundary)
- 반례 시나리오: 변조 클라이언트가 설치 지점에서 Triggered를 연속 호출한다. 하루 3장 상한은 지켜지지만 정상 플레이어가 6초 동안 수행하는 설치를 즉시 마친다. 채취도 같은 방식으로 단축한다. 반복 거부 요청으로 본인 알림을 쌓고 서버의 불필요한 처리를 늘린다. 착륙 연출 중에는 로버 탑승 요청이 phase 검사 없이 받아들여질 수 있다.
- 목적에 해로운 이유: 교사가 비교하는 소요 시간과 학생 행동 기록에 서로 다른 규칙이 적용된다. 비용과 자원 상한이 서버 권위라는 사실만으로 작업 시간까지 서버 권위가 되는 것은 아니다.
- 구체적 제안: 홀드 시작과 완료 때 생존, phase, 거리, 동일 대상 여부를 서버에서 검사하고 서버 시각으로 설치 2초, 채취 3초를 확인한다. 시작 이벤트 자체도 신뢰하지 않는다. 채취는 전 구간의 동일 운전자 상태를 확인한다. 홀드 없는 요청은 플레이어별 0.25초 간격으로 제한하고 거부 토스트는 같은 사유를 1초에 1번만 보낸다. 탑승에도 playing 검사를 추가한다. 아래 표의 프롬프트 전체에 같은 검증 헬퍼를 적용한다.
- 예상 작업량: M

### F06. 공유 자원 외의 협력은 선택 가능한 노동 병렬화에 머문다

- 심각도: 높음
- 근거: `src/server/ResourceState.luau:18`은 기지 상태 하나를 보유한다. 설치, 착공, 하역은 플레이어 역할을 사용하지 않는다. 채취만 운전자에게 제한된다. `src/server/DevMap.luau:1131`은 운전석 하나를 만들고, `src/client/Main.client.luau:28`은 기본 플레이어 목록도 숨긴다. 개인별 담당, 기여, 지원 요청을 복제하는 데이터는 없다. GDD 3절의 확정 구조는 서버당 기지 하나, 최대 4명이다.
- 반례 시나리오: 익숙한 학생 한 명이 운전과 착공을 모두 맡는다. 다른 학생은 설치 지점에서 하루 3장 한도를 공유하고, 총 30장 설치가 끝나면 자기에게 주어진 일이 사라진다. 심사위원이 나머지 두 명에게 지금 무엇을 판단하고 있는지 물으면 기다리고 있다는 답만 나온다. 솔로 클리어도 가능한 구조라는 사실과 4명 협력을 학습한다는 주장은 별개다.
- 목적에 해로운 이유: 결과 화면의 기지 물 원정 횟수는 누가 협력했는지 설명하지 못한다. 함께 접속한 인원수만으로 문제 해결 능력의 공동 학습을 증명할 수 없다.
- 구체적 제안: 전력 담당, 운송 담당, 건설 담당의 선택 가능한 역할과 현재 작업을 Player Attribute로 복제한다. 네 번째 플레이어는 지원 역할을 맡는다. 행동 권한을 잠그지 않아 1인 플레이와 결원 대응을 유지한다. 기지 HUD에는 담당자, 원정 중 여부, 물 요청 한 개를 표시한다. 서버에서 설치 장수, 실제 하역량, 착공 수를 사용자별로 기록하고 결과 화면에 기여를 함께 보여준다. 성공 조건에 2인 동시 버튼을 추가하지 않는다.
- 예상 작업량: M

### F07. 서버 구동 코드만 있고 네트워크 소유권과 경사 대응 계약이 없다

- 심각도: 높음

- 심각도: 중간
- 근거: `docs/SETUP.md:76`은 각 개발자가 rojo serve를 실행해 플레이스에 연결하도록 안내하지만 공유 플레이스의 동기화 담당자를 정하지 않는다. `:123`은 Workspace를 자유 편집 영역이라고 설명하지만 `default.project.json:29`는 Workspace.Gravity를 소유한다. `src/server/DevMap.luau:1755`는 LandingPads 폴더 존재만으로 전체 맵 자동 생성을 생략한다. `src/server/LandingSite.luau:136`은 패드가 없으면 경고 후 반환하며 사용자가 보는 실패 복구 화면은 없다.

- 목적에 해로운 이유: 코드 리뷰가 통과해도 공개 플레이스의 맵과 코드 조합은 검증되지 않는다. 마지막으로 누가 동기화했는지가 데모 버전을 결정한다.
- 구체적 제안: 공유 제출 플레이스에는 Rojo 연결자 한 명만 두고 main의 합의된 SHA만 동기화한다. 다른 개발자는 개인 테스트 플레이스를 쓴다. 맵 작업은 임시 이름에서 끝낸 뒤 LandingPads와 IceSites를 함께 확정한다. 시작 전 클래스, Pad1부터 Pad4, Ice1부터 Ice3, SpawnPoint, DriverSeat, 슬롯 30개, 모듈 3개의 필수 구조를 한 번에 검사하고 실패하면 게임을 시작하지 않고 대상 이름을 운영자에게 표시한다. 제출 직전 코드 SHA와 플레이스 버전을 함께 고정하고 로컬 백업을 남긴다. ### 서버 권위와 보안 판정표

Remotes 목록의 클라이언트 발신 이벤트는 SelectSite, SetSpeed, RequestRestart 세 개다. 프롬프트는 RemoteEvent가 아니지만 같은 클라이언트 입력 경계로 심사했다. 표의 엔진 거리 검사는 Triggered에 적용되는 Roblox 기본 검사이며 프로젝트의 독립 검증과 구분한다. Player 인자는 엔진이 제공한다. 페이로드가 없는 요청에 타입 검사가 없다는 사실만으로 취약점이라고 판정하지 않는다.

악의적 클라이언트가 할 수 있는 최악의 행동은 같은 기지의 진행을 망치거나 비용을 우회하는 것이다. 배속을 원정자 의사와 무관하게 2로 바꾸고, 복구 콘솔에서 반복 귀환으로 차량을 독점하며, 결과가 뜨자마자 지울 수 있다. 홀드 시간을 생략할 수 있다. 자동 네트워크 소유권을 얻은 운전자라면 로버를 비정상적으로 옮겨 거리 검사를 통과시키는 운송 우회도 방어되지 않는다. 반대로 SelectSite를 비권한자가 확정하거나 SetSpeed에 임의 숫자를 넣거나, 자원 증가량과 건설 비용을 Remote 인자로 직접 조작하는 경로는 현재 코드에 없다. Triggered의 기본 거리 검사를 무시하고 모든 고정 프롬프트를 맵 어디서나 실행할 수 있다고 단정하지 않는다.

### 정책과 에셋 라이선스 판정

현재 확인한 소스에는 개인정보 입력 폼, 외부 웹 요청, 사용자 자유 문장을 중계하는 Remote가 없다. 산소 0도 `src/server/Oxygen.luau:103`에서 착륙선 이동으로 처리하고 `src/shared/Config.luau:300`은 구조 표현을 쓴다. 이 구현에서 산소 고갈이라는 소재 자체가 정책 위반이라고 판정할 근거는 없다. 콘텐츠 설문은 실제 공개 화면과 효과를 기준으로 답해야 하며 교육 목적이라는 설명으로 면제되지 않는다. [콘텐츠 등급 안내](https://en.help.roblox.com/hc/en-us/articles/8863284850196-Content-Maturity-FAQ)

고정된 한국어 UI 문자열을 FilterStringAsync에 넣지 않았다는 이유만으로 필터 위반이라고 할 수 없다. 현재 수신 Remote는 임의 문장을 받아 표시하지 않는다. chooserName과 산소 알림은 플랫폼 DisplayName을 사용하며 이를 임의 채팅 입력과 동일하게 취급하지 않는다. 향후 학생이 기지 이름이나 자유 요청을 입력하고 다른 학생에게 표시하는 기능을 붙이면 서버에서 TextService:FilterStringAsync를 거치고 필터 실패 시 표시하지 않아야 한다. 예를 들어 학생이 전화번호를 기지 이름으로 입력해 전원에게 그대로 보이는 경우가 실제 필터링 문제다. [공식 텍스트 필터링](https://create.roblox.com/docs/ui/text-filtering)

Quaternius 공식 Ultimate Space Kit 페이지는 CC0를 명시한다. 따라서 공식 원본을 사용한 무료 교육 게임이라는 조건에서 라이선스 충돌을 단정할 근거는 없다. 다만 `docs/ASSETS.md:36`은 Sketchfab 표기와 설명의 차이를 기록하고 있으므로 실제 받은 파일의 출처와 라이선스 사본을 남겨야 한다. 출처가 다른 재업로드 파일을 CC0라고 간주하면 심사위원의 에셋 권리 질문에 답하지 못한다. 게임 설명에는 제작자와 팩 이름을 적고, 실제 라이선스와 다른 CC-BY 표기를 기계적으로 복사하지 않는다. [제작자 공식 라이선스](https://quaternius.com/packs/ultimatespacekit.html)

## 3. 실행 우선순위 요약

### 데모 전 반드시

- F01, F09: 실제 대상 계정과 심사 기기에서 접속하고 네 명이 같은 서버에 있는 것을 확인한다. MaxPlayers 4, 공개 자격, 설문, 아이콘, 썸네일, 계정과 앱 안내, 공개 버전 기록을 제출 경로와 함께 완성한다.
- F02: 탑승자 강제 원격 귀환과 물 보존 귀환을 막는다. 동료가 복구를 눌렀을 때 원정자가 버려지는 시나리오를 없앤다.
- F03, F04: 준비 후 시작, 책임자 배속, 10초 결과 읽기 시간을 보장한다. 초기 상태와 회차를 다시 받는 경로를 만든다.
- F05: 홀드 경과 시간과 요청 빈도, 탑승 phase를 검증한다. 일일 상한과 건설 비용 검사는 유지한다.
- F06: 담당자와 현재 작업, 지원 요청 한 개를 보여줘 네 명이 맡은 일을 말할 수 있게 한다. 역할별 독점 권한은 만들지 않는다.
- F07, F08: 공개 서버의 두 클라이언트로 주행과 입퇴장을 확인하고, 스트리밍 상태에서도 레이더 점 세 개와 귀환 지점이 유효한지 검증한다. 입력이 끊기거나 좌표가 사라지면 시연 차단 문제로 다룬다.
- F10: 게임패드 표시 A와 실제 X 불일치를 고친다. 지원한다고 제출할 기기에서 물 원정 전체를 한 번 끝낸다.
- F11, F12, F13: 실제 시연 기기의 입장 시간과 FPS를 측정한다. 템플릿과 에셋을 동결하고 공유 플레이스 Rojo 담당자와 Git SHA를 고정한다.

### 있으면 좋음

- F14: 산소, 자원 부족, 완공 소리와 작업 대상 Highlight부터 추가한다. 전체 음향 연출보다 이 네 신호의 구별을 먼저 검증한다.
- 역할별 기여를 결과에 표시하고, 실제 완공과 구조 없는 승리에 배지를 준다. 학생이 누가 무엇을 해결했는지 설명하는 보조 자료로 사용한다.
- F07: 경사 주행에서 실제 접지 문제가 남을 때만 서스펜션을 교체한다. 저사양 기기에서 측정된 병목이 있을 때 바위 메시와 충돌을 더 줄인다.
- 권한자 퇴장 시 선택 시간을 최소 10초 보장하고 늦게 입장한 학생의 조작 안내를 보완한다.

### 하지 말 것, 과잉 설계 경고

- DataStore, 글로벌 순위, MessagingService 교역, 여러 플레이스 이동을 데모 직전에 추가하지 않는다. 네 명이 같은 기지에서 실제로 협력하는 문제를 먼저 해결한다.
- 역할을 나눴다는 표시를 만들기 위해 건설과 운전을 특정 사용자에게 영구 잠그거나 2인 동시 버튼을 승리 조건에 추가하지 않는다. 결원과 1인 심사에 바로 막힌다.
- 스트리밍을 회피하려고 기지와 170개 바위를 전부 Persistent로 만들지 않는다. 레이더에 필요한 세 좌표부터 독립시킨다.
- 170개 Clone을 170회 메시 업로드나 별도 다운로드라고 설명하지 않는다. Neon을 PointLight 수에 포함하거나 측정 없이 성능 실패를 선언하지 않는다.
- 고정 한국어 문구를 전부 필터 API에 보내거나 산소 구조를 임의의 정책 위반으로 분류하지 않는다. 실제 사용자 자유 입력과 실제 공개 콘텐츠를 기준으로 판정한다.
- 계정과 공개 자격 문제를 결제나 연령 설정 편법으로 해결하려 하지 않는다. 접근 가능한 시연 범위와 학생 공개 가능 범위를 정확히 나눈다.

## 4. 확신 낮음 항목과 검증 한계

- 최신 실행 결과: `lune run tests/run.luau`에서 순수 규칙 30개 통과, 서버 스모크 OK 259, 실패 0, 스레드 오류 0, 경고 0이다. 검토 중 기존 스모크 파일이 갱신되어 최신 상태로 다시 실행한 결과를 사용했다. 리뷰 작업으로 코드와 테스트를 수정하지 않았다. 에뮬레이션 통과는 실제 네트워크나 GPU 동작의 증거가 아니다.
- F01: 공식 공개 조건과 SETUP의 누락은 확인했다. 실제 계정 자격, 대상 연령 도달 상태, 심사위원 계정, 행사 네트워크, MaxPlayers와 현재 Public 상태는 저장소에서 확인할 수 없다. 실제 배포가 이미 막혔다고 단정하지 않는다.
- F03: UI 준비와 시작이 서버 계약에 없다는 사실은 확인했다. RemoteEvent에는 버퍼가 있으므로 초기 이벤트가 반드시 유실된다고 쓰지 않았다. 저속 로딩과 재접속에서 스냅샷 수신 및 화면 복구를 실제 클라이언트로 확인해야 한다.
- F07: 1인 Studio의 W 전진은 제공된 기록을 인정한다. 입력 복제 실패, 소유권 전환 지연, 실제 전복 빈도는 확인하지 못했다. VehicleSeat 입력이 절대 서버에 복제되지 않아 현재 로버가 전혀 움직이지 않는다는 주장은 하지 않는다.
- F08: StreamingEnabled와 실제 반경은 퍼블리시된 플레이스에서 확인해야 한다. 레이더의 로컬 인스턴스 의존성은 코드로 확인했지만 점 소실, 늦은 충돌 로드, 귀환 화면의 구체적 증상은 재현하지 못했다. PadSignUI에는 추가된 Pad를 다시 탐색하는 처리가 있어 표지판 전체가 영구 소실된다고 단정하지 않는다.
- F10, F11: 잘못된 게임패드 키 표시는 코드와 공식 기본값으로 확인했다. 모바일 차량 조작, 조작 영역 겹침, 서버 부팅 시간, FPS, 메모리, 실제 메시 삼각형 수는 측정하지 못했다. PointLight 5개는 생성 코드 기준이며 외부 모델에 포함된 추가 조명은 포함하지 않는다.
- F12: 실제 MeshId, 이미지 승인, 업로드 소유권, 텍스처 상태와 공개 플레이스의 템플릿은 저장소에 없다. 행성의 지구 무늬, 건물 안쪽 면과 출입구의 실제 화면도 확인하지 못했다.
- 플레이테스트 기록의 지형, 하늘, 산소 구역은 검토 코드에서 후속 구현이 진행된 상태다. 현재 DevMap은 Terrain을 켜고, ClockTime 2.5와 태양 텍스처, Persistent 행성을 만들며, 건물 내부 산소 판정을 생성한다. 따라서 예전 기록의 태양 없음, 지형 롤백, 건물 옆 회복을 현재 확정 결함으로 반복하지 않았다. 개선된 화면의 완성 여부는 Studio 확인이 필요하다.
